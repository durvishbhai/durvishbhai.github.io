# 12 · Phase 5: bug reports, website warranty and support tickets

Status: **built and tested** (see "Test results"). Phase 6 has **not** been started. There is no "Phase 4" in this repository: the quotation, invoice and payment modules were never requested or built, so every place that would touch money is an explicit, documented integration point (see "Dependencies and limits") and never a simulated success.

## What exists

| Area | Capability |
|---|---|
| **Bug reports** | A client reports a bug on one of **their own** projects: reference `BUG-YYYY-NNNN`, title, description, affected URL, steps to reproduce, expected and actual behaviour, browser and device (typed, plus the captured user agent), up to 3 attachments or screenshots, submission timestamp, client-assessed severity (Low / Normal / High / Critical), status, and the warranty position at that moment. Can be saved as a **draft** (invisible to staff, no notification) and submitted later. Retried submissions are idempotent (one report, one notification). |
| **Severity vs priority** | Severity is how serious the problem is (the client proposes it; staff change it **with a reason**). Priority is how urgently staff schedule it (`low/normal/high/urgent`, internal, never shown to clients, changes need a reason). Both changes are recorded in the history and audit log. **No response time is promised anywhere**: `config/support.php -> sla` ships empty; with it empty no ticket is ever shown as overdue. |
| **Bug statuses** | Open, Triaged, Confirmed, In Progress, Fixed, Client Verification, Closed, Need More Information, Unable to Reproduce, Rejected with Explanation (+ Draft). The transition table is in `config/workflow.php` (`bug_transitions`) and is enforced on the server for every actor: S = staff handling the bug (`bugs.manage`), F = fixer (`bugs.fix`, only the assignee unless the person also holds `bugs.manage`), K = closer (`tickets.close`), C = the owning client. Every move is stored in `ticket_activity` and audited. Rejected / Unable to Reproduce / Need More Information require a written explanation that the client sees. |
| **Client verification** | The client **confirms** a fix (Client Verification -> Closed) or **reopens** with a written explanation (min. 10 characters). A client can never triage, confirm, start or mark fixed. A closed ticket can be reopened by the client within `TICKET_CLIENT_REOPEN_DAYS` (default 30); after that they are asked to open a new ticket and mention the reference. **Nothing closes automatically**: not a client reply, not an upload, not a thank-you message. A client reply to "Need more information" simply returns the report to Open. |
| **Website warranty** | Per project: eligibility (eligible / not applicable), duration in months (default 6, configurable per project), **start-date basis** (final delivery, client acceptance, manually confirmed contractual date), start date, calculated end date, related quotation/agreement reference (free text until the quotation module exists), versioned terms (`warranty_terms`), project-specific terms, admin notes, suspension with reason, full history (`warranty_history`) and audit. Status is **derived at read time** from those facts and today's date in the application time zone: Not Applicable, **Pending Confirmation**, Scheduled, Active, Expired, Suspended. |
| **Eligibility review** | On submission the system only chooses the queue: warranty Active -> *Awaiting technical review*; anything else -> *Submitted for assessment*. A reviewer (`bugs.review_eligibility`) records **Covered**, **Not covered** or **Potentially chargeable** with a client-facing explanation, the terms relied on, optional considerations (new feature, scope change, client modification, third-party failure, hosting/domain/API, unsupported environment: recorded only, none excludes automatically), reviewer, timestamp and whether a quotation is required. The client is told the outcome and the explanation. |
| **Chargeable issues** | *Potentially chargeable* never charges anything. Staff with `tickets.propose_change` create a **draft cost proposal** (scope, client-facing reason, cost in paise, days/date, snapshot of the original approved baseline) on the same `change_requests` record Phase 3 uses for revisions (linked by `ticket_id`). Staff send it; **only the owning client** approves or declines. **Work on a chargeable bug cannot move to In Progress until a proposal is approved.** An approved proposal is the client's recorded consent only: it does not touch `price_revisions`, the approved quotation, or any invoice. |
| **Support tickets** | Categories: Bug Report, Technical Support, Project Query, Billing, Payment, Account Access, Domain and Hosting, General Enquiry, Other. Optional link to one of the client's projects. Statuses: Open, Assigned, In Progress, Awaiting Client Response, Awaiting Internal Team, Resolved, Closed, Reopened (`support_transitions`). Assigning an open ticket moves it to Assigned and unassigning returns it to Open. |
| **Conversation** | Client-visible messages (`ticket_messages`) and internal notes / technical findings / decisions (`ticket_notes`) are **different tables**; no query for the conversation can return a note. Author and role are set by the server from the session. Workers cannot write to clients. Messages and attachments are idempotent via a form token. |
| **Attachments** | Phase 3 `FileStore` is reused unchanged: allow-list, MIME + signature check, random private storage outside the web root, scanner hook (fail-closed), `scan_status` never "clean" unless a scanner ran. Client-visible vs internal-only files. Downloads: `/tickets/{ticket}/files/{file}` authorised per ticket, per role and per visibility, rate limited, audited, served as `application/octet-stream` attachments with `nosniff`. |
| **Dashboards** | `/support/dashboard` (needs `support.dashboard`): open, unassigned, high/critical, awaiting client, awaiting internal team, fixed awaiting verification, escalated, past first-response target (**only when a target is configured**), and warranty counts: active, ending within `WARRANTY_EXPIRING_DAYS` (30), expired, start date not confirmed. `/tickets` is the queue with search, kind, status, category, severity, priority, assignee, project, created-date range (calendar days in the application time zone), escalated filter, pagination. `/warranties` is the warranty report with status and "ending soon" filters. All lists use the same visibility rule as a single record (a test compares them for every user and ticket). |
| **Client Support Centre** | `/support`: Report a bug, Create a ticket, open and resolved counts, unread replies, drafts, warranty summary. `/tickets` (client view): All / Open / Resolved / Drafts with search. Ticket page: description, conversation with attachments, history, warranty review outcome, cost proposals, confirm/reopen controls. `/support/warranty` and the project's Warranty tab: dates, duration, basis, terms (never admin notes). |
| **Notifications** | In-app (Phase 3 `Notifier`): new bug/ticket, client reply, staff reply, assignment, status changes, fix ready to verify, eligibility decision, cost proposal sent and decided, escalation. Deduplicated per user and event instance. **No email is sent and no notification claims one was** (`email_status` stays `not_sent`). |
| **Audit** | `ticket.created`, `.draft_saved`, `.client_reply`, `.staff_reply`, `.internal_note`, `.technical_finding`, `.internal_file`, `.assigned`, `.unassigned`, `.status_changed`, `.closed`, `.reopened`, `.severity_changed`, `.priority_changed`, `.escalated`, `.eligibility_decided`, `.eligibility_overridden`, `.file_downloaded`; `change_request.created/proposed/client_approved/client_declined/withdrawn` (with `ticket_id`); `warranty.configured/changed/dates_changed/suspended/resumed/terms_recorded`. Entries hold ids, field names and lengths, never message or note text. |

## Warranty date and eligibility rules (exact)

1. **The start date is never guessed.** It comes only from an explicit, recorded date **and** basis. A completed project, an approved deliverable or a published version are shown to the administrator as *hints* on the warranty page ("Project marked completed", "Last client approval", "Last deliverable published") and are never written automatically.
2. No record + service category *website development* -> **Pending Confirmation**. No record + any other service -> **Not Applicable**. A record without a start date -> **Pending Confirmation**. In both cases no dates are shown or invented.
3. **End date** = the same calendar day `N` months after the start, clamped to the last day of a shorter month (31 Aug + 6 months = 28 Feb, 29 Feb in a leap year; 31 Jan + 1 month = 28 Feb). **The end date is the last covered day** (inclusive). `WARRANTY_END_DAY_BEFORE=true` switches to "the day before" if the contract is worded that way. Tests pin 8 date cases plus both modes.
4. **Time zone.** "Today" is the date in `APP_TIMEZONE` (`AppTime`), never UTC. Tests freeze time around midnight in Asia/Kolkata to prove the boundaries (a warranty that starts on the 10th is Active from 00:00 local on the 10th and Expired from 00:00 local the day after the last covered day).
5. Status: `not_applicable` (eligibility) > `suspended` > `pending_confirmation` (no dates) > `scheduled` (today < start) > `active` (start <= today <= end) > `expired`.
6. **Inside the period is not "covered".** Every bug is decided individually (see below). Outside the period is not "rejected" either: the client can still submit, it goes to *Submitted for assessment*, and a person decides.
7. **Who may do what.** Configuring the warranty (duration, basis, dates, terms, suspension, new terms version) needs `warranty.manage`: **Administrator and Super Admin only**, plus the account password; every change needs a reason once a warranty exists, and is stored in `warranty_history` and the audit log. Managers and Support can view (`warranty.view`).
8. **Eligibility decisions.** A reviewer (`bugs.review_eligibility`, Manager and above) may record *Covered* only if the warranty was **Active when the bug was reported** (the snapshot stored with the report). *Not covered* and *Potentially chargeable* are ordinary decisions. **Covering an issue the warranty did not cover, or changing an earlier decision, is an override**: it needs `warranty.override` (Administrator), is flagged `eligibility_overridden`, and is audited as `ticket.eligibility_overridden` with the before/after values. A decision cannot be changed while a cost proposal for the issue is pending or approved.
9. Stored per decision: outcome, client-facing reason, terms relied on, considerations, quotation-required flag, reviewer, timestamp, override flag; the internal note and considerations go to the staff-only notes table.

## Permission controls

| Rule | Where it is enforced |
|---|---|
| A client sees only their own tickets and drafts (drafts only the author) | `TicketAccess::role` + `scopeSql`; 404 for others; IDOR tests for pages, replies, status posts and downloads |
| Workers: technical categories on assigned projects only; no billing/payment/account tickets; cannot reply to clients; no financial proposals | `TicketAccess` + `TicketQuery::changes` |
| Staff: all tickets (`tickets.view_all`), or assigned tickets and tickets on assigned projects (`tickets.view_assigned`) | `TicketAccess` |
| Internal notes, assignee, priority, escalation, reviewer, considerations never reach a client | Separate tables, `TicketAccess::forClient`, `TicketQuery` (shaped at the data layer); tests scan everything a client receives for marker strings |
| Staff identities are not shown to clients ("Vertex support team") | `TicketQuery::conversation/activity` |
| Only Administrators change contractual warranty data or override a decision | `warranty.manage`, `warranty.override` (sensitive), step-up password |
| Only the client approves extra cost | `ChangeRequestService::clientDecide` (owner + `revisions.respond_cost`) |
| Financial detail only for roles that handle it | cost proposals hidden from workers; clients see only non-draft proposals addressed to them |
| Administrators do not act as clients | client-only permissions (`bugs.report`, `tickets.create`, `tickets.view_own`, `tickets.reply_own`, `warranty.view_own`) are excluded from the Administrator role |

## Migration `0009_support_warranty.sql` (forward-only, additive)

New tables: `warranty_terms`, `project_warranties`, `warranty_history`, `tickets`, `bug_reports`, `ticket_messages`, `ticket_notes`, `ticket_files`, `ticket_activity`, `ticket_reads`. One nullable column on `change_requests` (`ticket_id`, FK RESTRICT). One data change: removes the Phase 0 default grants of `warranty.manage` from Manager and Support (the permission had no function before this phase). All foreign keys into projects, clients, files and tickets are `RESTRICT`; no existing row is modified. After upgrading run `php bin/console.php migrate` and `php bin/console.php permissions:sync` (new permissions get their defaults; roles you edited in the UI keep your edits).

New configuration (`.env`, see `.env.example`): `WARRANTY_DEFAULT_MONTHS` (6), `WARRANTY_END_DAY_BEFORE` (false), `WARRANTY_EXPIRING_DAYS` (30), `TICKET_CLIENT_REOPEN_DAYS` (30), `UPLOAD_TICKET_MAX_MB`. Rate limits in `config/auth.php`: `ticket_create_user` (20/hour), `ticket_message_user` (60/hour).

## Dependencies and limits (honest)

* **No quotation, invoice or payment module exists.** The "related quotation/agreement" on a warranty is free text. A chargeable bug produces a *change request* (consent record) that a future quotation module must turn into a quotation revision/invoice; `quotation_ref` on the change request stays empty until then. **Nothing is ever added to an invoice.**
* **Email**: not built. Clients are told in-app only; no text claims an email was sent.
* **Client-facing SLA**: none. If the business decides on a first-response target, set `support.sla.first_response_hours` in `config/support.php`; only then do "past target" counts and filters appear.
* The warranty status is derived on read; no scheduled job is needed and none is claimed. "Expiring soon" is computed, not notified (an expiry reminder needs the Phase 7 scheduler and an approved channel).
* Attachment scanning is the Phase 3 hook (`UPLOAD_SCANNER`); without a scanner files are recorded `not_scanned`.
* Webhook/e-mail replies do not exist, so there is nothing that could auto-close or auto-reply to a ticket.
* The warranty terms wording is **not shipped**: the business records its own signed wording as a new terms version. No legal text is invented.

## Manual testing checklist

1. Sign in as the dev client (`alpha`): *Support* -> *Report a bug*, choose your project, fill the fields, attach a PNG, **Save as draft**. Sign in as a manager: the draft is not listed. Back as the client open the draft, submit. The manager now sees it and has a notification.
2. As an administrator open the project -> *Warranty*: it says **Pending Confirmation** and shows no dates. Record eligible, 6 months, start date, basis *Final delivery*, password. The end date is calculated and shown; the history shows the change; the audit log has `warranty.configured`.
3. As a manager open the bug: *Warranty review*. Try **Covered** on a bug reported before the start date: refused (needs an administrator). Record **Potentially chargeable** with an explanation: the client page shows the outcome and the "any additional work will be quoted first" sentence.
4. Create a draft cost proposal, send it. As the client open the notification, approve. Only now can the manager move the bug to *In Progress*. Check `price_revisions` is unchanged.
5. Move the bug Triaged -> Confirmed -> In Progress -> Fixed -> Client Verification. As the client confirm (closes) or reopen without an explanation (refused) and with one (reopens).
6. As a developer assigned to the project open a technical ticket (allowed), a billing ticket (refused), add an internal note; confirm the client cannot see it. As another client, paste a ticket URL: 404.
7. As the client create a support ticket, answer "Awaiting client response", confirm the status returns to Open. Resolve and close.
8. Open `/support/dashboard` and `/warranties` as a manager and as a client (client is refused).
